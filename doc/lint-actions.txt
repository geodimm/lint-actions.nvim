1. INTRODUCTION                                    *lint-actions-introduction*

Some linters tell you how to fix what they found. That fix normally has
nowhere to go, because Neovim's code-action menu only listens to LSP servers.

lint-actions.nvim gives those fixes a way in. It runs a small LSP server
inside Neovim that serves code actions and nothing else, so linter fixes turn
up in |vim.lsp.buf.code_action()| and in any picker that speaks LSP.

It does not run linters, and it does not replace the code-action UI.

Neovim 0.11 or newer is required.

===============================================================================
2. SETUP                                                  *lint-actions-setup*

                                                        *lint_actions.setup()*
`setup({opts})`
    Starts lint-actions. The core has no dependencies: >lua

      require('lint_actions').setup()
<
    The bundled integrations need nvim-lint. Configure nvim-lint first, then
    turn on the tools you use with `true`, or with a table to change
    something: >lua

      require('lint_actions').setup({
        integrations = {
          nvim_lint = {
            golangci = true,
            markdownlint = {
              source = 'my-markdownlint',
            },
            shellcheck = true,
          },
        },
      })
<
    You can call `setup()` again later to turn on more integrations, and
    turning on one that is already on does nothing. `false` means "leave it
    off"; it will not turn off an integration you enabled earlier.

    Integrations reuse output from lint runs you already trigger and never
    run a linter themselves. See |lint-actions-integrations| for what each
    one needs.

3. INTEGRATIONS            *lint-actions-integrations* *lint-actions-adapters*

Bundled integrations reuse nvim-lint's output instead of running the linter a
second time. The reusable SARIF adapter attaches through the generic nvim-lint
bridge. Each has its own guide: ~

  golangci-lint                                        |lint-actions-golangci|
  markdownlint                                     |lint-actions-markdownlint|
  shellcheck                                         |lint-actions-shellcheck|
  SARIF (reusable)                                         |lint-actions-sarif|

Those guides cover requirements, configuration, which actions you get, and
tool-specific caveats.

NVIM-LINT ADAPTER API                                 *lint-actions-nvim-lint*

nvim-lint runs the linter process and publishes diagnostics, but it leaves
reading the output to each linter's `parser` function. lint-actions wraps that
parser and leaves the diagnostics alone: ~

  1. nvim-lint runs the configured command.
  2. The linter's parser turns the output into `vim.Diagnostic[]`.
  3. lint-actions hands the same raw output and those diagnostics to the
     adapter.
  4. The adapter returns code-action items.
  5. The original diagnostics go back to nvim-lint unchanged.

Any function-based nvim-lint parser can be hooked this way. To connect one to
your own adapter: >lua

  require('lint_actions.integrations.nvim_lint').attach({
    linter = 'linter-name',
    adapter = require('my_adapter'),
    source = 'optional-source-override',
    configure = optional_function,
  })
<
`linter` takes a registered nvim-lint name or a linter definition. The adapter
must have a `source` field and a `parse(context)` function.

On its own, `attach()` does not touch the linter's command or arguments. Use
`configure` for that.

CHANGING THE OUTPUT FORMAT ~

An adapter often needs structured output that the default parser cannot read
— JSON instead of plain text, say. Adding a `--json` argument alone would
break diagnostics, because the old parser would be reading the wrong format.
The argument and the parser have to change together.

You can do that by hand before attaching: >lua

  local lint = require('lint')
  local adapter = require('my_json_adapter')
  local linter = lint.linters.my_linter

  table.insert(linter.args, '--json')
  linter.parser = adapter.diagnostics

  require('lint_actions.integrations.nvim_lint').attach({
    linter = linter,
    adapter = adapter,
  })
<
The replacement parser must take `(output, bufnr, cwd)` and return
`vim.Diagnostic[]`. The adapter's `parse(context)` then receives
`context.output`, `context.bufnr`, `context.cwd`, and those diagnostics as
`context.diagnostics`.

Editing the linter by hand only works if it is a plain table. nvim-lint also
lets a linter be a factory, which is rebuilt on every run and throws your
changes away each time. Pass `configure` and lint-actions applies it wherever
the linter came from: >lua

  require('lint_actions.integrations.nvim_lint').attach({
    linter = 'my_linter',
    adapter = adapter,
    configure = function(linter)
      linter.args = linter.args or {}
      table.insert(linter.args, '--json')
      linter.parser = adapter.diagnostics
    end,
  })
<
`configure` gets the resolved linter just before its parser is wrapped, and
runs once per linter. Since it has to run before the wrap, attaching without
`configure` and adding one afterwards raises an error rather than quietly
leaving the arguments alone.

|lint-actions-markdownlint| is a full worked example of this pattern.

SARIF 2.1.0 tools can share the bundled
`require('lint_actions.adapters.sarif')` adapter. It reads standard
`result.fixes` entries, including multi-artifact fixes. Attach it through the
same API and give each tool a distinct `source`. See |lint-actions-sarif|.

If you already have finished actions, skip nvim-lint entirely and call
|lint_actions.publish()|. To run raw output through an adapter yourself, use
|lint_actions.ingest()|.

4. PUBLISHING                                           *lint-actions-publish*

Every fix belongs to a source: a stable string naming whatever produced it.
There are two ways to get a source's fixes into the menu.

  - `publish()` hands over fixes when you have them. Good for fixes that come
    out of a tool when it finishes running.
  - Registering a provider hands over a function that is called when Neovim
    asks. Good for fixes you can work out from the buffer on the spot. See
    |lint-actions-providers|.

WHAT SOURCE IS FOR ~

`source` is a replacement key, nothing more. Publishing again for the same
source replaces only that source's actions, so several sources can share a
buffer without coordinating.

Neovim never shows it. The code-action menu labels an entry with the LSP
client name, `lint-actions`, and only when the buffer has more than one client
attached.

To name your tool in the menu, put it in `action.title` as a bracketed suffix.
The golangci-lint adapter titles its actions `Apply suggested fix [errcheck]`,
which reaches the menu as `Apply suggested fix [errcheck] [lint-actions]`. A
suffix beats a prefix: it stacks with Neovim's own label, and actions stay
sorted by what they do rather than clumped under whoever made them.

                                                      *lint_actions.publish()*
`publish({opts})`
    Replaces the actions for one buffer and source. An empty `items` list
    clears that source.

    Fields: ~
      bufnr   Buffer the actions belong to.
      source  Stable name for whatever produced them.
      items   List of `{ range = range, action = action }`. Each action is an
              `lsp.CodeAction`, except that its `edit` may also be one
              `lsp.TextEdit` or a list of text edits aimed at `bufnr`.

    An item's `range` says where the action shows up. Matching is by line:
    `character` is accepted so the shape stays valid, but it never narrows
    anything. Leave `range` out to offer the action anywhere in the buffer.

    For an ordinary same-buffer fix, use the TextEdit shorthand: >lua

      action = {
        title = 'Apply suggested fix',
        kind = 'quickfix',
        edit = { range = edit_range, newText = replacement },
      }
<
    `publish()` wraps text edits in a versioned `lsp.WorkspaceEdit` for you.
    Supply a full WorkspaceEdit when the fix touches several files or renames
    things. Either form can be diffed by a preview-capable picker; an action
    that carries only a command usually cannot.

FIXES THAT ARE NOT EDITS ~

    If a fix cannot be written as a text edit, an action can carry an
    `lsp.Command` instead of, or alongside, an edit. lint-actions passes it
    through untouched and Neovim runs it client-side, so register the handler
    before you publish: >lua

      vim.lsp.commands['my-tool.run'] = function(command, context)
        run(command.arguments[1], context.bufnr)
      end
<
    Neovim looks the name up in `vim.lsp.commands` and in the client's own
    command table before asking the server. lint-actions advertises no
    `executeCommandProvider`, so an unregistered name does not run — Neovim
    warns that the server does not support the command. Use an edit when you
    can: edits can be previewed, are checked against the buffer version, and
    undo in one step.

                                                        *lint_actions.clear()*
`clear({opts})`
    Clears one source for a buffer. Omit `source` to clear all of them.

                                                       *lint_actions.ingest()*
`ingest({opts})`
    Runs tool output through `opts.adapter` and publishes what comes back.

5. PROVIDERS                                          *lint-actions-providers*

A provider is the pull side of |lint-actions-publish|. Instead of tracking
when your fixes change and pushing them, you give lint-actions a function and
it calls you when Neovim asks for code actions. There is nothing to keep
fresh — no autocmds, no debouncing — because you read the buffer as it is at
that moment.

Note that you do not list your own source in `setup()`. That option names
bundled integrations only, and rejects anything else so a typo is reported
rather than ignored. Call |lint_actions.publish()| or
|lint_actions.register()| directly; both call `setup()` for you, so order does
not matter.

                                                     *lint_actions.register()*
`register({provider})`
    Registers a provider. Registering the same `source` again replaces the
    earlier one.

    Fields: ~
      source     Stable name for whatever produced the actions.
      provide    `fun(context): items`. Called synchronously on every
                 request. May return `nil` for no actions. `context` carries
                 `bufnr`, the requested `range`, and `only` when the client
                 filtered by kind. Returned items are matched the same way
                 published ones are.
      filetypes  Optional list limiting the provider to those filetypes.
      enabled    Optional `fun(bufnr): boolean` limiting it further.

    Example: >lua

      require('lint_actions').register({
        source = 'my-tool',
        filetypes = { 'lua' },
        provide = function(context)
          if not needs_fix(context.bufnr) then
            return {}
          end
          return {
            {
              action = {
                title = 'Apply my fix',
                kind = 'quickfix',
                edit = { range = edit_range, newText = replacement },
              },
            },
          }
        end,
      })
<
    `provide` runs while Neovim waits for the answer, so it has to be
    synchronous and quick — a slow provider holds up the menu. If your fixes
    come from a process, publish them instead.

    If `provide` throws, the error is reported with |vim.notify()| and that
    provider is skipped. Other providers and published actions still answer
    the same request.

    Registering a provider attaches the in-process client to the ordinary
    file buffers it applies to (`buftype` empty), including ones already
    open. Declaring `filetypes` keeps that narrow.

    `examples/foldmarker.lua` in the repository is a small working provider.
    It offers to add a fold marker modeline to a buffer that uses fold
    markers but has no modeline: it reads the buffer, returns a rangeless
    whole-buffer item, and uses `enabled` to stay out of the way elsewhere.
    It is an example rather than a bundled integration — copy it into your
    config and call its `setup()`.

                                                   *lint_actions.unregister()*
`unregister({source})`
    Removes a provider. Buffers stay attached and simply stop getting actions
    from that source.

6. HEALTH                                                *lint-actions-health*

Run `:checkhealth lint_actions`. It shows the Neovim version requirement,
every attached nvim-lint integration, and every registered provider.

A misconfigured integration would otherwise fail silently, because
lint-actions only ever sees output that nvim-lint produces. So the check warns
when: ~

  - an attached linter is in no `linters_by_ft` entry, so nvim-lint never runs
    it and no actions are ever published
  - nvim-lint has no linter under the attached name
  - a linter's command is not executable

A missing nvim-lint is not reported here. Attaching a linter by name needs it,
so |lint_actions.setup()| already fails when it is absent.
